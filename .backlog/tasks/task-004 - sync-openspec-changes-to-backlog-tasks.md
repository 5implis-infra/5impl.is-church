## Why

OpenSpec changes are the canonical source for planning and design, but the team uses Backlog for daily Kanban-style execution tracking. We already sync `docs/` ↔ `.backlog/docs/` and `docs/adrs/` ↔ `.backlog/decisions/` via pre-commit hooks. We need a similar integration for OpenSpec changes and Backlog tasks so that an OpenSpec change can be projected onto the Backlog board without duplicating rich artifact content.

## What Changes

- New sync script: `tsx scripts/sync-openspec-change-to-backlog.ts`
- New reverse sync script: `tsx scripts/sync-backlog-task-to-openspec.ts`
- New pre-commit hook: `scripts/.git/sync-openspec-changes-to-backlog.sh`
- Backlog task files generated under `.backlog/tasks/` (active) and `.backlog/archive/` (archived)
- Backlog task bodies are **self-contained snapshots** with embedded content from OpenSpec artifacts (no external `@see` links)
- Only controlled fields sync back from Backlog to OpenSpec: status, checklist progress, notes, final summary
- Documentation: `docs/OPENSPEC-BACKLOG.md`
- AGENTS.md update with integration reference

## Capabilities

### New Capabilities

- `openspec-backlog-task-sync`: Generates a Backlog task from an OpenSpec change. The Backlog task contains self-contained embedded snapshots of OpenSpec proposal, design, specs summary, tasks, and plan. Frontmatter includes board metadata (status, labels, references to OpenSpec paths). Sync is one-way from OpenSpec to Backlog for content; Backlog can push back controlled fields.

- `openspec-backlog-archive-sync`: When an OpenSpec change is archived, generates or updates an archived Backlog task under `.backlog/archive/`. Removes the active Backlog task if it was generated by the sync (not manually created).

- `openspec-backlog-field-back-sync`: Reads Backlog task for status changes, checklist progress updates, and notes/final summary. Updates the corresponding OpenSpec change metadata (`.openspec.yaml` progress, notes) only for controlled fields.

# Brainstorm: Sync OpenSpec Changes to Backlog Tasks

## Agreed Scope

**Goal**: Bi-directional sync between OpenSpec changes and Backlog tasks, where:
- OpenSpec remains the canonical source for scope, specs, design, and implementation plan
- Backlog tasks serve as operational Kanban projections (board tracking, status, execution notes)
- Backlog task bodies must be **self-contained** — the Backlog UI only navigates `.backlog/`, so external links like `@see openspec/...` or `@see docs/...` in body sections are NOT supported; instead, referenced content must be embedded/inlined as snapshots
- Sync covers both **active** and **archived** changes

**In Scope**:
- Generate one Backlog task per active OpenSpec change (`.backlog/tasks/`)
- Generate one Backlog task per archived OpenSpec change (`.backlog/archive/`)
- Sync OpenSpec → Backlog: full content snapshots in body sections
- Sync Backlog → OpenSpec: only controlled fields (status, checklist progress, notes/final summary)
- Snapshot-based sync (one-way content copy with controlled round-trip for metadata)
- Backlog tasks must be parseable by Backlog CLI/MCP when available
- Documentation: `docs/OPENSPEC-BACKLOG.md` explaining the ownership model

**Out of Scope**:
- Full two-way content round-trip (not a docs/adrs-style mirror)
- Automatically desarchiving OpenSpec from manual Backlog archive actions
- Creating Backlog subtasks for each OpenSpec tasks.md item by default

## Key Constraints

1. **Backlog UI navigates only `.backlog/`** — body sections cannot reference external paths; content must be embedded as self-contained snapshots
2. **OpenSpec is canonical** — rich artifacts (proposal, design, specs, plan) are not overwritten by Backlog content
3. **Backlog CLI not installed locally** — validation must support both direct markdown parsing and CLI/MCP when available
4. **Existing pre-commit hooks** for `docs/` ↔ `.backlog/docs/` already exist — new scripts must not conflict

## Alternatives Considered

**A. Full two-way content mirror (like docs/adrs sync)**
- Treat Backlog task body as canonical equivalent of OpenSpec artifacts
- Allows editing in both directions with conflict resolution
- Rejected because: OpenSpec artifacts (proposal, design, specs, plan) have richer structure and longer生命周期 than Backlog task bodies; Backlog is better as an operational projection

**B. Backlog as pure index (links only, no embedded content)**
- Backlog task body contains only `@see openspec/...` and `@see docs/...` references
- No content duplication
- Rejected because: Backlog UI cannot follow external links; content would be unreadable in Backlog context

**C. OpenSpec as canonical + Backlog as operational projection (CHOSEN)**
- OpenSpec remains source of truth for all planning artifacts
- Backlog receives self-contained snapshots for readability
- Only controlled fields (status, progress, notes) sync back to OpenSpec
- Matches how each tool is used: OpenSpec for design/planning, Backlog for execution tracking

## Chosen Direction

```
┌─────────────────────────────────────────┐
│  openspec/changes/<change>/             │
│  proposal.md / design.md / specs/**     │
│  tasks.md / plan.md / verify.md         │
└────────────────────┬────────────────────┘
                     │ OpenSpec → Backlog (snapshot)
                     ▼
┌─────────────────────────────────────────┐
│  .backlog/tasks/task-N - <title>.md    │
│  frontmatter: board metadata + refs    │
│  body: embedded snapshots (PROPOSAL,   │
│        DESIGN, TASKS, PLAN, etc.)      │
└────────────────────┬────────────────────┘
                     │ Backlog → OpenSpec (controlled fields only)
                     ▼
         Controlled: status, checklist progress,
         notes, final summary
```

**Snapshot sections use markers**:
```markdown
## OpenSpec Proposal
<!-- OPENSPEC:PROPOSAL:BEGIN -->
<full content>
<!-- OPENSPEC:PROPOSAL:END -->
```

**Status mapping**:
```
OpenSpec active + 0% tasks checked  → Backlog status: To Do
OpenSpec active + partial progress   → Backlog status: In Progress
OpenSpec active + all verified      → Backlog status: Done → archive
OpenSpec archived                   → Backlog archived task
```

**Archive lifecycle**:
```
OpenSpec change archived
  → generate/update .backlog/archive/<task>.md
  → remove .backlog/tasks/<task>.md (if generated by sync)
```

## Context

OpenSpec changes are the canonical source for planning and design in this monorepo. The team also uses Backlog for task/board tracking. We already have bidirectional sync hooks for `docs/` ↔ `.backlog/docs/` and `docs/adrs/` ↔ `.backlog/decisions/`. We need a similar integration for OpenSpec change artifacts and Backlog tasks, enabling an OpenSpec change to appear as a Backlog task on the operational board.

The Backlog tool only navigates files under `.backlog/`. Its UI cannot follow external links to `openspec/changes/...` or `docs/...`. For a Backlog task to be readable and actionable, its body must contain embedded content (snapshots) from the referenced artifacts rather than links.

## Goals / Non-Goals

**Goals:**
- Project each active OpenSpec change as a self-contained Backlog task under `.backlog/tasks/`
- Project each archived OpenSpec change as a self-contained Backlog archived task under `.backlog/archive/`
- Keep Backlog task bodies readable by embedding full snapshots of OpenSpec artifact content
- Enable status/progress/notes to flow back from Backlog to OpenSpec for operational tracking
- Validate generated Backlog tasks by parsing their markdown structure
- Reuse the existing pre-commit hook pattern established for docs ↔ backlog docs sync

**Non-Goals:**
- Full two-way content round-trip (Backlog task body does not overwrite OpenSpec artifacts)
- Automatic de-archiving of OpenSpec changes from manual Backlog archive actions
- Creating Backlog child subtasks for each item in OpenSpec tasks.md by default
- Replacing the existing `docs/` ↔ `.backlog/docs/` or `docs/adrs/` ↔ `.backlog/decisions/` sync hooks
- Supporting Backlog as the primary planning tool (OpenSpec remains canonical)

## Decisions

**D1. OpenSpec is canonical for content; Backlog is an operational projection**

OpenSpec artifacts (proposal, design, specs, tasks, plan, verify) are the source of truth. Backlog tasks receive embedded snapshots from these artifacts. Only controlled metadata fields (status, checklist progress, notes, final summary) can flow back from Backlog to OpenSpec. This matches how each tool is used: OpenSpec for design/planning, Backlog for execution.

Alternatives considered:
- B1: Full two-way mirror (like docs/adrs sync). Rejected because OpenSpec artifacts have richer structure and longer lifecycle than Backlog task bodies; Backlog is better as an operational projection.
- B2: Pure index with links only. Rejected because Backlog UI cannot follow external links.

**D2. Backlog task bodies embed content via snapshot markers, not external links**

Each relevant OpenSpec artifact is embedded in a dedicated section with a marker like `<!-- OPENSPEC:PROPOSAL:BEGIN -->...<!-- OPENSPEC:PROPOSAL:END -->`. The frontmatter `references` and `documentation` fields MAY contain paths to OpenSpec files (for script/agent reference), but body sections must contain the actual content.

Rationale: Backlog UI only navigates `.backlog/`. External `@see openspec/...` or `@see docs/...` links in body sections would be unreadable in the Backlog context.

**D3. Snapshot sections are generated but preserve a regeneration marker**

Snapshots include a header noting they are generated and pointing to the canonical source:
```markdown
## OpenSpec Proposal
*This section is generated from OpenSpec. Edit the OpenSpec artifact, not this snapshot.*
```

This makes it clear to human editors that changes should happen in OpenSpec, not in the Backlog task body.

**D4. Status mapping is derived from OpenSpec tasks.md progress**

| OpenSpec tasks.md state | Backlog status |
|---|---|
| 0% checklist items checked | `To Do` |
| Partial checklist progress | `In Progress` |
| All items checked + verified | `Done` → trigger archive |

This avoids manual status management and keeps Backlog board in sync with OpenSpec execution.

**D5. Archive lifecycle: OpenSpec archives → Backlog archives**

When OpenSpec marks a change as archived, the sync script:
1. Generates or updates `.backlog/archive/<task-id> - <title>.md` with full snapshots (including verify/retrospective if present)
2. Removes the corresponding active task in `.backlog/tasks/` if it was generated by sync (has marker and no manual content outside controlled sections)

Manual Backlog archive actions do NOT trigger OpenSpec de-archiving.

**D6. Backlog CLI/MCP validation is optional with graceful degradation**

The sync scripts validate generated task files by:
1. Parsing frontmatter and body structure directly (required, always runs)
2. Attempting `backlog task list --plain` to verify Backlog can parse the file (optional, warns if CLI unavailable)

This mirrors the approach used in the existing `backlog-sync-docs-to-backlog.ts` script.

**D7. New pre-commit hook, separate from existing docs ↔ backlog hooks**

The new hook `scripts/.git/sync-openspec-changes-to-backlog.sh` runs `tsx scripts/sync-openspec-changes-to-backlog.ts` when OpenSpec change files are staged. This is additive and does not modify existing `backlog-sync-docs-to-backlog.sh` or `backlog-sync-backlog-to-docs.sh`.

## Risks / Trade-offs

- **Risk**: Backlog task body becomes stale if OpenSpec artifacts change without re-running sync.
  - **Mitigation**: Pre-commit hook keeps active tasks in sync on every commit. A periodic verification task (in verify.md) checks for drift.

- **Risk**: Simultaneous edits to OpenSpec artifacts and Backlog task notes cause merge conflicts.
  - **Mitigation**: OpenSpec artifacts are canonical for content; Backlog notes are in a separate section (`Implementation Notes`) that does not overlap with snapshot sections. Clear marker boundaries prevent accidental overwriting of snapshots.

- **Risk**: Large OpenSpec artifacts bloat Backlog task files.
  - **Mitigation**: Only core content is embedded. Binary assets, large code samples, or very long specs may be summarized rather than fully embedded. This is a judgment call per artifact; the script truncates if content exceeds a reasonable threshold (e.g., 500 lines).

- **Risk**: CLI/MCP validation unavailable in some environments.
  - **Mitigation**: Direct markdown parsing validation always runs. CLI/MCP validation is best-effort with a warning if unavailable.

## ADDED Requirements

### Requirement: openspec-backlog-task-generation

Feature: OpenSpec Change to Backlog Task Projection

Rule: Each active OpenSpec change generates exactly one Backlog task file under `.backlog/tasks/`

#### Scenario: Generate Backlog task from active OpenSpec change
- **GIVEN** an OpenSpec change directory `openspec/changes/<change-id>/` exists with at least `proposal.md`
- **WHEN** the sync script runs for that change
- **THEN** a file is created at `.backlog/tasks/<task-id> - <title>.md`
- **AND** the file contains valid Backlog task markdown with YAML frontmatter
- **AND** the frontmatter includes `id`, `title`, `status`, `labels`, `references`, and `documentation` fields
- **AND** the body contains embedded snapshots of all OpenSpec artifacts present (proposal, design, specs summary, tasks, plan, verify)

#### Scenario: Backlog task body is self-contained with embedded snapshots
- **GIVEN** an OpenSpec change with `proposal.md`, `design.md`, and `tasks.md`
- **WHEN** the Backlog task is generated
- **THEN** each artifact content is embedded in a dedicated section with a marker pair (e.g., `<!-- OPENSPEC:PROPOSAL:BEGIN -->...<!-- OPENSPEC:PROPOSAL:END -->`)
- **AND** no external `@see openspec/...` or `@see docs/...` links appear in body sections
- **AND** the frontmatter `references` field MAY contain OpenSpec paths for script/agent reference

#### Scenario: Backlog task status is derived from OpenSpec tasks.md progress
- **GIVEN** an OpenSpec change with `tasks.md` containing checkbox items
- **WHEN** the sync script evaluates task progress
- **THEN** if 0% of checklist items are checked, status is `To Do`
- **AND** if some but not all items are checked, status is `In Progress`
- **AND** if all items are checked and verified, status is `Done`

#### Scenario: Generated task has regeneration marker
- **GIVEN** a Backlog task generated from an OpenSpec change
- **WHEN** the task body is read
- **THEN** each embedded section contains a header noting it is generated from OpenSpec
- **AND** a marker `generated-by: openspec-backlog-sync` or similar is present in the frontmatter

### Requirement: openspec-backlog-archive-projection

Feature: OpenSpec Archive to Backlog Archive Projection

Rule: When an OpenSpec change is archived, its Backlog projection moves to the archive folder

#### Scenario: Archive OpenSpec change creates archived Backlog task
- **GIVEN** an OpenSpec change `openspec/changes/<change-id>/` is marked as archived
- **WHEN** the sync script runs
- **THEN** a file is created or updated at `.backlog/archive/<task-id> - <title>.md`
- **AND** the archived task contains all snapshots including verify and retrospective if present

#### Scenario: Active Backlog task is removed after OpenSpec archive
- **GIVEN** an OpenSpec change transitions from active to archived
- **WHEN** the sync script processes the archive event
- **THEN** if `.backlog/tasks/<task-id> - <title>.md` exists and was generated by sync (has the generation marker)
- **THEN** that active task file is removed
- **AND** if the task has manual content outside controlled snapshot sections, it is NOT removed and a warning is logged

#### Scenario: Archived OpenSpec change updates existing Backlog archive task
- **GIVEN** an OpenSpec change is re-edited after being archived (e.g., verify.md updated)
- **WHEN** the sync script runs
- **THEN** the archived Backlog task under `.backlog/archive/` is updated with the new content
- **AND** the active `.backlog/tasks/` folder is NOT recreated

### Requirement: openspec-backlog-field-reverse-sync

Feature: Controlled Field Reverse Sync from Backlog to OpenSpec

Rule: Only specific controlled fields flow from Backlog task back to OpenSpec change
